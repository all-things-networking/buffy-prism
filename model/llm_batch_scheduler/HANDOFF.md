## 1. TL;DR (the one-paragraph version)

We model a GPU worker running **chunked-prefill continuous batching** (the vLLM-V1
default). A tagged interactive request (the "victim", short prompt + modest output)
competes for batch slots with background traffic on equal terms. Bad event = the
victim suffers a **token-latency stall** (its inter-token gap exceeds an SLO). We ask
how the *shape of the request mix* drives that probability. **Headline result
(non-obvious, validated):** under chunked prefill, `P(interactive stall)` is
**invariant to the long-*prompt* fraction** and driven entirely by the long-*output*
fraction — i.e. the danger is the one feature the scheduler **cannot observe at
admission**. Prompt-length-based scheduling (the intuitive lever) is aimed at the
wrong variable.

## 3. The model (`scheduler_queue.pm`) in one page

**Type:** DTMC. **Time** = scheduler *iterations* (one forward pass over the running
batch). Horizon `T`.

**Records.** PRISM has no arrays, so we spell out `M` **unified request records**. Each
record is `st ∈ {0 empty, 1 waiting, 2 running}` plus fields `pp` (prompt blocks left to
prefill), `oo` (output blocks left to decode), `bk` (KV blocks currently held), `ad`
(arrival time, for FCFS order). Record 1 = the **victim** (carries gap counters — pure
instrumentation, *no scheduler privilege*, see Q3 below). Records 2..M = background.

**One iteration = a sweep through these stages** (the `stage` variable):
1. `VINJECT` — at `t = T_V`, the victim appears as a `waiting` record. (Its arrival time
   is an *input assumption*, like q5's idle-then-active schedule in FQ-CoDel — its own
   input, not a privilege.)
2. `ARRIVE` — with prob `p_arr`, one background request arrives into the lowest empty
   record. Its prompt is long w.p. `p_lp`; its output is long w.p. `p_ol_sp` or `p_ol_lp`
   **conditioned on prompt class** (this is the correlation knob — set them equal for
   independent lengths).
3. `ADMIT` — promote `waiting → running` while `nrun < N_SLOTS`, in FCFS-by-arrival order
   (`ADM_POLICY=0`) or SJF-by-prompt order (`ADM_POLICY=1`). This is the **queue**: waiting
   records are the queue; admission drains it.
4. `SVC_k` (one stage per record) — each running record does one iteration of work:
   prefill `min(pp, CHUNK_BLK)` blocks, else decode one output block, else finish and free
   its slot + KV. The victim's stages bump its inter-token **gap counter** when it is *not*
   making decode progress; `v_maxgap` tracks the worst gap.
5. `PREEMPT` — if total KV `> KV_CAP`, evict running→waiting by LIFO (`POLICY=0`) or
   protect-the-victim priority (`POLICY=1`), looping until KV fits; evicted requests return
   to the queue and must recompute lost blocks.

**Key formulas** (search these strings in the file):
- `formula key_i = ADM_POLICY=1 ? pp_i : ad_i;` — admission order (arrival vs prompt length).
- `formula sc_i = (run_i & bk_i>0) ? (ad_i + priority-adjust) : -1;` — eviction victim.
- Arrival branch probabilities factor as `p_arr * {p_lp} * {p_ol|class}`.

**Bad-event labels** (bottom of file): `v_stalled` (`v_maxgap ≥ SLO_TBT`, the main one),
`v_preempted`, `cascade` (`preempts ≥ K_CASC`), `done` (`t = T`).

**Sweepable constants (leave undefined, pass with `-const`):** `T_V, N_SLOTS, KV_CAP,
CHUNK_BLK, POLICY, ADM_POLICY, p_arr, p_lp, p_ol_sp, p_ol_lp`. Shapes `SP/LP/SO/LO/VP/VO`
are defined in-file (edit to change ratios).

## 4. Design decisions and their FQ-CoDel parallels

These four came out of a design review; they're what make the model defensible to a
reviewer.

- **Q3 — the victim gets no scheduler privilege.** It's an ordinary record admitted/evicted
  by the same rules as background. What's allowed to be "its own" is its **input** (a short
  shape, a fixed arrival time) — exactly as q5 in FQ-CoDel had its own idle-then-active
  schedule but no special queue treatment. "Picking one request as the victim doesn't lose
  generality." *This is the single most important correctness property; don't reintroduce a
  victim privilege.*
- **Q6 — prompt and output length are decoupled**, drawn independently (with an optional
  correlation knob). Real requests aren't perfectly correlated, and — as it turned out — the
  decoupling is exactly what lets the headline finding (prompt irrelevant, output decisive)
  even be *expressible*.
- **Q8 — there is a real waiting queue**, and eviction returns a request to it (recompute),
  rather than dropping it. This is what puts *queueing delay* (the real harm) in scope.
- **Assumptions are RANGES, not points.** Same standard as incast/FQ-CoDel: the deliverable
  is a **monotone parameter box**, certified at its least-favorable corner, not a single
  tuned operating point. See §7.

## 5. The investigation arc (what was tried, in order)

1. **v1 (`scheduler.pm`)** — privileged victim, dedicated slot, 3-concurrent. Found
   "victim gets preempted, driven by LIFO **timing** not volume." *Then we distrusted it.*
2. **v2 redesign (`scheduler_queue.pm`)** — de-privileged per Q3/Q6/Q8. **Caught our own
   artifact:** with a realistic slot limit the small victim can never push KV over the cap,
   so `P(victim preempted) = 0`. The v1 preemption headline was partly a setup artifact. The
   *robust* harm is **queueing delay** (waiting for a slot behind long requests). Timing story
   survives here too (long request *before* victim → 2× stall; same longs *after* →
   protective). See `NOTES_queue.md` §"robust finding".
3. **"Is this obvious?" check** — an expert would find "long-heavy mix hurts interactive
   latency" *obvious* (it's the subfield's founding motivation). So we explored **four**
   candidate non-obvious directions (honest outcomes in `NOTES_queue.md`):
   1. SJF-by-prompt backfire — **refuted** (SJF helps the short victim, as expected).
   2. Adding capacity backfires — **partial**: more KV helps, but raising `N_SLOTS` at fixed
      KV trades queueing-stall for preemption thrash.
   3. Priority blind spot — **confirmed but secondary**: eviction-priority does nothing for
      *queueing* delay (identical `P(stall)` to FCFS).
   4. Prompt↔output correlation — **refuted** (tiny, obvious-direction effect).
4. **The realism fix that unlocked the headline.** With `CHUNK_BLK=1`, a long prompt takes
   many iterations to prefill, artificially inflating prompt importance. Realistically a
   chunk ≫ a prompt, so a prompt prefills in ~1 iteration (`CHUNK_BLK ≥ LP`). Under the
   *realistic* setting, the headline (§6) appears.
5. **SMC validation at scale** (§8) — confirmed the headline isn't a toy-scale artifact.

## 6. The headline finding

> **Under chunked prefill, `P(interactive stall)` is invariant to the long-*prompt*
> fraction and monotone ↑ in the long-*output* fraction.**

On the exact model (realistic prefill, `N_SLOTS=1`, `p_arr=0.8`), sweeping `p_lp × p_ol`:
every column is identical across `p_lp` rows (spread 0.000), and rises 0.64 → 0.86 → 0.96
across `p_ol`. (See the grid in `NOTES_queue.md` §"THE non-obvious finding".)

**Mechanism:** chunked prefill collapses any prompt into ~1 iteration, so prompt length no
longer affects how long a request holds a slot — only *output* length does (one decode
iteration per output block). The victim's queueing delay is set purely by how long
incumbents hold slots = their **output** length.

**Why it matters (the paper hook):**
- It **contradicts** the standard worry that long-*context* (long-prompt) requests threaten
  interactive latency. Chunked prefill *neutralizes* prompt length for this bad event.
- The residual danger is **output length** — the one quantity the scheduler **cannot see at
  admission** (primer's known/unknown asymmetry). So prompt-based admission/routing/priority
  is aimed at the wrong variable; you'd need output-length *prediction*.
- It's a "the SOTA mitigation moved the bottleneck" story: chunked prefill fixed the
  long-prompt stall and thereby made output length the sole driver.

## 7. The paper deliverable — a monotone parameter box (Flavor B)

Two forms exist; the second is the paper-ready one.

**(a) Composition-beats-load box** (`NOTES_queue.md` §"candidate paper assumption").
`P(stall)` is monotone ↑ in `p_lp, p_ol, p_arr` (verified on the sweep grid: 0/72, 0/48,
1/64 violations), so a box over them is certified at its lower corner:
`A = { p_arr ∈ [0.6,0.8], p_lp ∈ [0.6,0.8], p_ol = 0.6 } ⇒ P(stall) ≥ 0.19`. The
non-obvious cut: moderate-load-long-heavy (0.359) starves the victim **3.5×** more than
high-load-short-mix (0.101) — shape dominates load.

**(b) Prompt-invariance / output-dominance box** (the stronger form):
> Under realistic chunked prefill, `P(interactive stall)` is **invariant to
> `p_lp ∈ [0,1]`** and monotone ↑ in the long-output fraction; e.g. `p_ol ≥ 0.5 ⇒
> P(stall) ≥ 0.86` *regardless of prompt lengths*. For multi-chunk prompts the prompt
> fraction re-enters in proportion to `prompt_blocks / CHUNK_BLK`, still dominated by output.

`T_V` (victim arrival time) is **non-monotone** (finite-horizon artifact) and is kept
*out* of the box as a fixed input assumption — worth revisiting (see §10).

## 8. SMC validation (`VALIDATION.md`, `run_smc_validation.sh`)

To rule out a toy-scale artifact, `gen_scheduler.py` emits the same model for arbitrary
`M`. **Cross-check:** generating `M=3, N_SLOTS=2` reproduces the hand-written
`scheduler_queue.pm` *exactly* (all probabilities match) — this is our generator-vs-model
equivalence check and substitutes for a separate oracle for now (see §10).

Big model: `M=8` records / `N_SLOTS=3` (oversubscribed), prompt 1-vs-8 blocks, output
1-vs-16, `T=40` — too large for exact, run via PRISM SMC (20k samples, 99% CI ≈ ±0.009):

| prefill chunk | vary long-**prompt** frac | vary long-**output** frac |
|---|---|---|
| `=8` (prompt in 1 chunk) | 0.473 / 0.481 / 0.476 → **flat** | 0.020 / 0.473 / 0.950 → **dominant** |
| `=4` (2 chunks) | 0.494 / 0.545 / 0.609 → modest | — |
| `=2` (4 chunks) | 0.528 / 0.879 → strong | — |

The finding holds and gets *sharper*: prompt length matters only ∝ chunks a prompt spans;
output dominates because it adds one iteration per token. Reproduce:
`source ~/buffy-prism-tools/env.sh && cd chunked && ./run_smc_validation.sh`.

## 9. Known limitations (all deliberate abstractions — flag these if a reviewer asks)

- **Toy magnitudes.** 1–8 slots vs ~256 real `max_num_seqs`; small `KV_CAP`; short horizons.
  Only the **ratios** are meant to be faithful (KV oversubscribed, long≈several× short,
  chunk vs prompt, arrivals > slots). `PARAMETERS.md` has the full real-vs-model table.
- **No TTFT bad event yet.** The queue exists, but we score the token-gap (TBT) stall, not
  time-to-first-token. Adding a TTFT SLO label is low-hanging fruit.
- **Victim arrival `T_V` fixed** (a legitimate input assumption, not a privilege) and
  non-monotone under the finite horizon — sweep it / lengthen the horizon to test robustness.
- **Correlation knob present but unexercised at scale** (`p_ol_sp` vs `p_ol_lp`) — the
  refutation in §5.4 was at the small scale.

## 10. Open threads / suggested next steps (in rough priority order)

1. **Independent Python oracle.** Both prior case studies shipped one. We have the
   generator↔hand-model exact-match check, which is strong, but a from-scratch Python
   simulator that reproduces a few `P(stall)` points would match the bar you set on FQ-CoDel.
   *Highest-value gap.*
2. **TTFT bad event.** Add a time-to-first-token SLO label to bring the classic
   admission-latency metric into scope; the queue already supports it.
3. **Robustness sweeps** on `T_V`, `KV_CAP`, `N_SLOTS`, and horizon — especially to
   understand/tame the `T_V` non-monotonicity so it could enter the box.
4. **Exercise the correlation knob at scale** via SMC (does prompt↔output correlation ever
   move the headline? small-scale said no).
5. **Write the case-study narrative** for the paper from `VALIDATION.md` + `NOTES_queue.md`
   §6–7. The story is: SOTA mitigation (chunked prefill) neutralizes the visible feature
   (prompt) and leaves the invisible one (output) as the sole driver of interactive-latency
   risk → prompt-based scheduling is misdirected.

**Gotchas I hit so you don't:**
- `W` is a reserved word in PCTL (weak-until) — the window const is named `WIN`.
- `-const` silently returns empty if you try to override a const that's *defined* in-file;
  sweepable consts are left undefined on purpose.
- The symbolic engine complained "probabilities sum to < 1" on an unreachable
  `t=T & stage=PREEMPT` state — fixed with the `t'=min(T,t+1)` clamp. Keep it.
- Sweeps: use PRISM **experiment mode** (`-const x=lo:step:hi`, one JVM) not a bash loop of
  JVM startups, or it takes forever.

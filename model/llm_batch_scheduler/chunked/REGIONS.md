# Regions — probabilistic (mild, non-obvious) vs. 100% (obvious)

Mirrors incast `example3_prob_vs_obvious`: a probabilistic tool finds **mild,
non-obvious** assumptions under which the stall is likely-but-not-certain, whereas a
**100% (certainty)** method can only certify the **obvious extremes**.

**Model:** `scheduler_mc.pm` — the realistic multi-chunk model. A long-context prompt
spans `LP=4` prefill chunks (4 prefill iterations); a long output is `LO=32` decode
iterations (ratio 8:1, conservative vs. real 10–64×). `CHUNK_BLK=1` (one chunk per
prefill iteration = realistic). `M=8` records, `KV_CAP=64`, horizon `T=64`. Generated by
`gen_scheduler.py`; too large for exact checking, so **SMC** (PRISM simulation, 12–15k
samples, 99% CI ≈ ±0.01). Bad event: interactive-latency stall `v_maxgap ≥ SLO_TBT`.

## Per-request law (corrected for realistic, multi-chunk prompts)

A long-**output** request harms the tracked request **~2–4× more** than a long-**context**
(multi-chunk prompt) request — because it holds its slot ~33 iterations vs. ~5:

| fraction f long (one dimension only) | long-prompt-only | long-output-only | ratio |
|---|---|---|---|
| 0.3 | 0.051 | 0.189 | 3.7× |
| 0.5 | 0.184 | 0.471 | 2.6× |
| 0.7 | 0.405 | 0.767 | 1.9× |

Prompt length is **not** irrelevant here — that was a single-chunk special case (see the
correction in `NOTES.md`). But output dominates, and output is the feature the scheduler
**cannot observe at admission**. The visible feature (prompt length) is the weaker predictor.

## Structural observation: sharp in provisioning, gradual in workload

`P(stall)` is **sharp** in the provisioning knob `N_SLOTS` and **gradual** in the workload:

```
  N_SLOTS (p_lp=p_ol=0.3):  2 -> 0.80   3 -> 0.37   4 -> 0.085   5 -> 0.007   6 -> 0
  p_ol   (at N=3, p_lp=0.3): 0.2 -> 0.25   0.3 -> 0.37   0.4 -> 0.50     (gradual)
  p_lp   (at N=3, p_ol=0.3): 0.2 -> 0.30   0.3 -> 0.37   0.4 -> 0.45     (gradual)
```

So the genuinely-uncertain region is a thin shell at the **provisioning knee** `N_SLOTS=3`
(as in incast: sharp in fan-in `M`, gradual in sync `WIN`). Above the knee (`N≥5`) it is
certainly safe; below (`N≤2`) it certainly stalls; only at the knee does the workload
composition decide.

## Obvious / provable regions (what a 100% method finds)

- **`A_under ≡ (N_SLOTS ≤ 2)`** — `P(stall) ∈ [0.80, 0.99]` across realistic workloads →
  "always stalls." Under-provisioned. Provable and obvious.
- **`A_over ≡ (N_SLOTS ≥ 5)`** — `P(stall) ≤ 0.007 ≈ 0` → "never stalls." Over-provisioned.
  Provable and obvious.

## Mild box — probabilistic, non-obvious (the payoff)

```
A_M ≡ (N_SLOTS = 3) ∧ (p_lp ∈ [0.2, 0.4]) ∧ (p_ol ∈ [0.2, 0.4]) ∧ (p_arr = 0.9)
```

| `P(stall)` | p_ol=0.2 | p_ol=0.3 | p_ol=0.4 |
|---|---|---|---|
| **p_lp=0.2** | 0.181 | 0.302 | 0.432 |
| **p_lp=0.3** | 0.247 | 0.369 | 0.498 |
| **p_lp=0.4** | 0.326 | 0.448 | 0.568 |

`P(stall) ∈ [0.18, 0.57]` at **every** point — none rare, none certain. Monotone increasing
in `p_lp` and `p_ol`, so the corners `(0.2,0.2)=0.18` and `(0.4,0.4)=0.57` certify the whole
box. The outcome hinges on the workload composition, dominated by the long-**output**
fraction — the quantity invisible at admission.

## Config-uncertainty region (operators don't yet know how to set `N_SLOTS`)

At a fixed realistic mix `(p_lp=0.4, p_ol=0.4, p_arr=0.9)`:

| `N_SLOTS` | 2 | 3 | 4 |
|---|---|---|---|
| `P(stall)` | 0.90 | 0.57 | 0.19 |

```
A_cfg ≡ (N_SLOTS ∈ {3,4}) ∧ (p_lp = 0.4) ∧ (p_ol = 0.4) ∧ (p_arr = 0.9)   →  P(stall) ∈ [0.19, 0.57]
```

The provisioning choice an operator cannot confidently make (3 vs. 4 slots per worker)
swings a realistic workload between a mild-high and a mild-low coin-flip; drop to 2 and it
crosses into the obvious-bad region. This is a probabilistic assumption that ranges a
**config** parameter, not just workload.

## The contrast (the methodological point)

| | `A_under` / `A_over` (obvious) | `A_M` / `A_cfg` (mild, non-obvious) |
|---|---|---|
| in words | under- or over-provisioned | realistically provisioned (3–4 slots), moderate workload |
| `P(stall)` | ≈1 or ≈0 everywhere | ∈ [0.18, 0.57] everywhere |
| certify `A ⟹ stall` (∀ / verification) | succeeds — but the assumption is the obvious extreme | **fails** — no point is certain |
| find a counterexample (∃) | trivial | exists, but ranks the same as a 20%-risk point |
| `P(stall \| A)` (probabilistic) | 1 or 0 (uninteresting) | **18–57% — the actionable answer** |

A 100%-method certifies only the provisioning extremes; the realistic knee regime is
invisible to it, and is exactly where a quantified `P(stall | A)` earns its keep — and it
says the risk is set by the **output-length mix you cannot observe at admission**.

## Reproduce

```bash
source ~/buffy-prism-tools/env.sh
python3 gen_scheduler.py --M 8 --SP 1 --LP 4 --SO 1 --LO 32 --VP 1 --VO 2 --T 64 --out scheduler_mc.pm
PRISM=~/buffy-prism-tools/prism-4.10.1-linux64-x86/bin/prism
# mild-box corner (repeat over the grid); monotone in p_lp,p_ol,p_arr and decreasing in N_SLOTS,
# so the corners bound every interior point:
$PRISM scheduler_mc.pm -pf 'P=? [ F ("done" & v_maxgap>=SLO_TBT) ]' \
  -const T_V=5,POLICY=0,ADM_POLICY=0,CHUNK_BLK=1,KV_CAP=64,p_arr=0.9,N_SLOTS=3,p_lp=0.2,p_ol_sp=0.2,p_ol_lp=0.2 \
  -sim -simsamples 15000 -simpathlen 4000
```

## Validation

The independent from-scratch oracle `sched_sim.py` (no PRISM) reproduces the PRISM/SMC
values above within CI at every corner — e.g. `(N=3, p_lp=.2, p_ol=.2)` oracle 0.183 vs
PRISM 0.181; `(N=3, .4, .4)` 0.564 vs 0.568; `N=2/3/4 (.3,.3)` 0.800/0.375/0.086 vs
0.802/0.372/0.085. This is example3's setup (incast's `incast_sim.py`), and it lets us go
to realistic magnitudes PRISM cannot reach — below.

# Realistic magnitudes (oracle `sched_sim.py`)

The regions above use the small PRISM-checkable model. The oracle — cross-checked against
PRISM at that scale — also runs at realistic token magnitudes. Config (tokens): prefill
**chunk 512**; prompt **short 16 / long 2048** (a long prompt = 4 prefill chunks); output
**short 8 / long 256** (a long output = 256 decode iterations → **64:1** vs a long prompt's
prefill cost); victim 16-tok prompt / 32-tok output; **Poisson load λ=0.3 req/iter**; batch
width `N_SLOTS` (the realistic knob; knee ≈ 20–24 here); `M=64` record pool; horizon
`T=400`, victim arrives `T_V=200`; KV pool generous (queueing-dominated). Reproduce with
`./run_regions_oracle.sh` (8k samples, 99% CI ≈ ±0.015).

## Per-request law sharpens at realistic ratios — output dominance is near-total

| fraction f long (one dimension) | long-**prompt** (2048-tok) only | long-**output** (256-tok) only |
|---|---|---|
| 0.3 | **0.000** | 0.332 |
| 0.5 | **0.000** | 0.967 |

A long-context (2048-token prompt) request causes **~zero** interactive stall; long-output
requests drive it to near-certain. The "prompt matters 2–4×" seen earlier was the small-`LO`
(=32) regime; at realistic `LO=256`, a long prompt's 4 prefill iterations are negligible
against 256 decode iterations. **So the strong claim — prompt length is nearly irrelevant,
output length drives it, and output is unobservable at admission — holds at realistic
magnitudes** (and is *stronger* than at toy scale, not weaker).

## Structure (realistic): sharp in provisioning, gradual in output fraction, flat in prompt

```
  N_SLOTS (p_lp=p_ol=0.3):  12->0.98  16->0.84  20->0.51  22->0.34  24->0.20  28->0.05  32->0.008
  p_ol   (N=22, p_lp=0.3):  0.22->0.06  0.26->0.17  0.30->0.34  0.34->0.54  0.38->0.71   (gradual)
  p_lp   (N=22, p_ol=0.3):  0.1->~0.34  0.5->~0.34  0.9->~0.35                            (flat)
```

## Obvious / provable regions (what a 100% method finds)

- **`N_SLOTS ≤ 16`** → `P ∈ [0.84, 0.98]`: always stalls (under-provisioned).
- **`N_SLOTS ≥ 28`** → `P ≤ 0.05`: never stalls (over-provisioned).
- **`p_ol ≤ 0.22`** (output-light workload) → `P ≤ 0.06`: never stalls.

## Mild boxes (probabilistic, non-obvious) — every point a coin-flip

Both range a variable no one controls well, hold prompt fraction **free** (it barely
matters, ≤0.05 swing), and are monotone so the corners certify the interior:

```
Workload box (ranges the INVISIBLE long-output fraction):
  A_w  ≡ (N_SLOTS = 22) ∧ (p_ol ∈ [0.26, 0.34]) ∧ (p_lp ∈ [0,1])   →  P(stall) ∈ [0.17, 0.54]

Config box (ranges the PROVISIONING knob operators can't set well; per review note 3):
  A_cfg ≡ (N_SLOTS ∈ [20, 24]) ∧ (p_ol = 0.3) ∧ (p_lp ∈ [0,1])     →  P(stall) ∈ [0.19, 0.56]
```

Corners: `A_w` min `(p_ol=0.26)=0.17`, max `(p_ol=0.34)=0.54`; `A_cfg` min `(N=24,p_lp=.9)=0.23`,
max `(N=20,p_lp=.9)=0.56` (min over the box `(N=24,p_lp=.1)=0.19`). No point rare, no point
certain. The outcome is set by provisioning and the **long-output fraction the scheduler
cannot observe at admission**; the visible feature (prompt length) does not move it.

## The contrast, at realistic scale

A 100%/reachability method certifies only `N_SLOTS ≤ 16` (always) and `N_SLOTS ≥ 28` (never)
— the provisioning extremes. The realistic operating regime — batch width at the knee
(20–24) with a moderate, partly-invisible output-length mix — is exactly the mild box, where
`P(stall | A) ∈ [0.17, 0.56]` is the actionable answer, and it points at the output-length
distribution as the lever, not prompt length.
